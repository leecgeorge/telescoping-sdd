# Feature: Artifact Ordering Prefix

**PLAN feature identifier:** `n/a`

## Objective

Prepend a two-digit ordinal prefix (`NN_`, e.g. `01_`, `02_`, `03_`) to each methodology artifact filename generated by the `telescoping-sdd` plugin, so that a directory listing of `blueprint/` or `specs/<dir>/` reads top-to-bottom in phase order rather than alphabetically. The mapping is: blueprint tier — `01_SCOPE.md`, `02_ARCHITECTURE.md`, `03_PLAN.md`; SDD tier — `01_spec.md`, `02_design.md`, `03_tasks.md`. Resolution is additive and backward-compatible: every read site either strips an optional leading `^\d{2}_` from an already-known basename before comparison (for exact-equality gates and frozenset membership tests), or probes the bare path first then falls back to the prefixed form (for the ~47 construct-then-stat read sites). Newly generated artifacts are emitted with the prefix by default (safe because the additive resolver tolerates both forms). A one-shot renamer (`artifact_prefix.py`) is provided for existing projects. The **content hash** is computed over file content only (not filename), so a pure rename never invalidates the content hash; however, the renamer must additionally preserve the `.sdd/pending-review.json` marker because that marker is keyed by relpath — not content — and a rename without the guard would orphan an in-flight panel-review obligation. This is a MINOR version bump; additive resolution (R1/R2) is non-breaking, default-on emission (R3) changes emitted filenames but the additive resolver, R7 surfacing, and the renamer keep it non-breaking for consumers, and the resolution-first sequencing is what makes default-on tolerable in a minor. This follows the precedent set by the 1.7.0 `specs/F<n>-<slug>/` directory rename, which was likewise a hash-safe, non-breaking minor.

## Requirements

### R1: Additive Resolution at Every Read Site

As a plugin maintainer, I want every code path that resolves an artifact by basename to tolerate both bare and prefixed forms, so that both `spec.md` and `01_spec.md` resolve to the same artifact and existing projects with bare names remain fully functional.

Resolution uses two helpers — both must be implemented:
1. `strip_artifact_prefix(name: str) -> str` — strips an optional leading `^\d{2}_` from a basename already in hand; used by the three exact-equality gates and the `TERMINAL_FILENAMES` frozenset membership test. The stripped result is honored **only when the stripped basename is in the known-artifact set** `{spec.md, design.md, tasks.md, SCOPE.md, ARCHITECTURE.md, PLAN.md}`; a stripped name not in that set is treated as a non-artifact file (no over-match, no resolution attempt).
2. `resolve_artifact(dir, bare_name) -> Path` — for the ~47 construct-then-stat sites: probe `dir / bare_name` first; if absent, probe `dir / "<NN>_<bare_name>"` (the prefixed form); raise an explicit ambiguity error if BOTH exist. **If NEITHER form exists, return the bare `dir / bare_name` path unchanged — do NOT raise.** Many call sites rely on graceful absence: `read_file(...) -> None` and `.is_file() -> False` soft gates (e.g. `find_project_root`'s `None` return, `classify_spec`'s `STATE_NOT_STARTED`, the `render_business_brief` missing-artifact gate, the previous-phase `exists: False` check). Raising on absence would convert those graceful misses into crashes; raising is reserved SOLELY for the both-exist ambiguity. This is the single chokepoint where ambiguity detection lives. All construct-then-stat call sites route through this helper.

**Acceptance Criteria:**

  THEN the validator locates and parses `01_spec.md` as the spec artifact and reports the same pass/fail result it would for bare `spec.md` with identical content

### R3: Default-On Prefixed Emission in Both Tiers

As a plugin end-user (practitioner), I want newly generated artifacts to be written to the prefixed path by default, so that a fresh project's `blueprint/` and `specs/<dir>/` directories sort in phase order immediately after generation, without any extra steps.

**R3 must not ship before R1 and R2 are fully implemented and green.** A fresh project's own newly-emitted `01_spec.md` will not resolve in the validators unless the resolver already tolerates the prefixed form at every site — shipping R3 first would cause a self-inflicted break.

**Acceptance Criteria:**

- GIVEN a fresh `telescoping-sdd` session with no pre-existing blueprint artifacts
  WHEN the `project-blueprint` skill generates the scope artifact
  THEN the phase reference (`phase-scope.md`), skill template, and any command examples in `SKILL.md` instruct the drafting agent to write to `blueprint/01_SCOPE.md`

- GIVEN a fresh `spec-driven-dev` session generating a spec
  WHEN the `spec-driven-dev` skill generates the spec artifact
  THEN the phase reference (`phase-specify.md`), skill template, and any command examples in `SKILL.md` instruct the drafting agent to write to `specs/<dir>/01_spec.md`

- GIVEN the emitted path instruction change in `phase-specify.md`
  WHEN the CFC binding obligation references the spec path
  THEN the path uses `01_spec.md` (all prose and command examples in the phase reference are internally consistent)

- GIVEN the `validate_spec.py --set-language` and `validate_blueprint.py --approve` command examples in phase references
  WHEN these examples reference artifact paths
  THEN they use the prefixed form (e.g. `03_PLAN.md` instead of `PLAN.md`)

### R4: Hash-Safe Renamer Helper

As a plugin end-user with an existing project using bare artifact names, I want a one-shot command that renames my bare artifacts to the `NN_` prefixed form without invalidating any content hash or approval, so that I can opt into sortable names without re-approving every artifact.

**Acceptance Criteria:**

- GIVEN a `blueprint/` directory containing approved `SCOPE.md`, `ARCHITECTURE.md`, and `PLAN.md` with valid content hashes
  WHEN the renamer is invoked (e.g. `python telescoping-sdd/scripts/artifact_prefix.py blueprint/`)
  THEN each file is renamed to its prefixed form (`01_SCOPE.md`, `02_ARCHITECTURE.md`, `03_PLAN.md`) and the content hash stored in each file remains valid (i.e. the additive resolver finds the renamed file and `verify_content_hash` returns True on the same content)

- GIVEN a `specs/<dir>/` directory containing approved `spec.md`, `design.md`, and `tasks.md`
  WHEN the renamer is invoked on that directory
  THEN each file is renamed to `01_spec.md`, `02_design.md`, `03_tasks.md` and all stored content hashes remain valid

- GIVEN the content hash is computed over file content only (not filename), as confirmed by `blueprint_common.content_for_hashing` (`blueprint_common.py:179`)
  WHEN the renamer renames a file without altering its content
  THEN `verify_content_hash(content, stored_hash)` returns True after the rename (content hash is filename-independent; a pure rename is hash-safe as long as the resolver finds the file by the new name)

- GIVEN a directory containing partially prefixed artifacts (e.g. `01_SCOPE.md` already renamed, `ARCHITECTURE.md` still bare)
  WHEN the renamer is invoked
  THEN it renames only the bare artifacts and leaves already-prefixed artifacts untouched (idempotent / re-runnable: a half-applied state from a prior interrupted run is recovered by re-running after the user fixes the cause)

- GIVEN a directory containing no recognizable bare artifacts
  WHEN the renamer is invoked
  THEN it exits with code 0 and prints a message indicating nothing to rename

- GIVEN a directory with a `.sdd/pending-review.json` entry keyed to an artifact in that directory (e.g. a pending panel-review obligation for `spec.md`)
  WHEN the renamer is invoked on that directory
  THEN the renamer exits non-zero, names the pending artifact, and tells the user to resolve or decline the pending review before renaming (REFUSE; do not silently rewrite the key — refusing is the conservative, auditable choice for v1; a future enhancement may offer key-rewrite). The refusal is **directory-scoped**: a pending entry for any single artifact blocks renaming the whole directory (including unrelated bare artifacts in it) — intentional for v1, since a partial rename around a pending obligation is the hazard being avoided

- GIVEN both `spec.md` AND `01_spec.md` already exist in the target directory (with any content)
  WHEN the renamer is invoked
  THEN the renamer exits non-zero and names both conflicting files — it must not create or worsen an ambiguity the resolver would choke on

- GIVEN the renamer encounters a file it cannot rename (permission error, target already exists with different content)
  WHEN the rename would fail
  THEN the renamer exits non-zero with a descriptive error message and does not partially rename the directory (atomic per-file: rename one at a time, halt and report on first failure)

The global ambiguity guarantee holds **because** every construct-then-stat site routes through the single `resolve_artifact` chokepoint — not via N independent local fallbacks, each of which would silently pick one and never observe both forms simultaneously.

**Acceptance Criteria:**

### R7: Mixed-State Surfacing and Renamer Discoverability

As a practitioner who upgrades mid-project, I want to be told when my project is in a **mixed** state (some artifacts bare, some prefixed — the worse-than-before sort state) and how to fix it, so that the sort benefit is reachable without depending on knowing the renamer command exists. (A uniformly-bare project is deliberately left silent — the sanctioned "keep bare names" state.)

Default-on emission means a practitioner who upgrades mid-project can end up with a directory like `spec.md, 02_design.md, 03_tasks.md` — the bare `spec.md` now sorts **after** the prefixed files (worse than before), and the renamer is undiscoverable without this surfacing.

**Acceptance Criteria:**

- GIVEN a `blueprint/` or `specs/<dir>/` in a genuinely **mixed** state — at least one bare artifact AND at least one prefixed artifact coexisting (the worse-than-before sort state R7 targets)
  WHEN a validator (`validate_spec.py` or `validate_blueprint.py`) runs on that directory
  THEN the validator emits a **non-blocking WARN** naming the bare artifacts and pointing to the renamer command (`artifact_prefix.py`) — the passive baseline beneath the interactive offer (see the interactive-offer AC below)

- GIVEN a **uniformly bare** directory (one or more bare artifacts, NO prefixed artifact present)
  WHEN a validator runs on that directory
  THEN it does NOT emit the mixed-state WARN — uniformly-bare is the sanctioned "keep bare names" state per the no-opt-out Boundary, and warning it on every run would contradict that promise (the WARN fires only once the directory becomes mixed, e.g. after the first prefixed artifact is emitted)

- GIVEN a **uniformly prefixed** directory (all artifacts prefixed, NO bare artifact present — the desired end-state of a fresh default-on project or a completed rename)
  WHEN a validator runs on that directory
  THEN it does NOT emit the mixed-state WARN (the WARN's trigger is the bare-AND-prefixed conjunction; a uniformly-prefixed directory is already correctly sorted and silent)

- GIVEN both a bare form and its prefixed counterpart exist (the ambiguity condition)
  WHEN the ambiguity error is raised
  THEN the error message states the recovery path (which file to remove, or that the user may run the renamer after resolving the conflict) — not just the two filenames. When the two files have **identical content**, the message says so explicitly and tells the user it is safe to remove either one (keeping the prefixed form for sortable names), since the resolver cannot choose a canonical file but the user loses nothing by deleting a byte-identical duplicate

- GIVEN the renamer is run on a directory in a half-applied state (e.g. it renamed SCOPE then hit a permission error on the next file)
  WHEN the user fixes the underlying cause and re-runs the renamer
  THEN already-prefixed files are skipped and the remaining bare files are renamed without error (idempotent / re-runnable). Note: a half-applied directory is itself a *mixed* state, so the mixed-state WARN above is the discoverability bridge that routes the user back into the interrupted rename — the two ACs describe the same directory state observed from two entry points

- GIVEN a project in a **mixed** state (at least one bare AND at least one prefixed artifact — the SAME trigger as the validator WARN, and explicitly NOT a uniformly-bare directory) AND an **interactive** session (a practitioner running the skill, not a non-interactive or CI invocation) [Q3, settled]
  WHEN the skill flow reaches an appropriate surfacing point (entering or resuming a workflow, or after a phase completes)
  THEN the skill **interactively offers** to run the renamer, in addition to the standalone CLI and the validator WARN. The offer mirrors the WARN's mixed-only trigger (three-state, matching the WARN ACs above): a **uniformly-bare** directory gets NO offer (the sanctioned "keep bare names" state — the offer must never nag the deliberate-bare user), a **uniformly-prefixed** directory gets NO offer (nothing to rename), and only a **mixed** directory is offered. The offer fires **at most once per session** and is **suppressed for the rest of the session after a decline**. The rendered prompt string itself must state that declining is fine and bare names stay valid via the additive resolver (the reassurance must be in the text the user reads, not merely an offer property). Both `project-blueprint` and `spec-driven-dev` carry the offer

- GIVEN the practitioner **accepts** the offer
  WHEN the skill runs the renamer on their behalf
  THEN the skill faithfully relays the renamer's exit status and message — including its refusals (R4's directory-scoped pending-review refusal, and the pre-existing-ambiguity refusal) and its idempotent no-op (R4 "nothing to rename → exit 0") — and never claims success when the renamer refused or no-opped. Because a mixed directory is also the state most likely to carry an open `.sdd/pending-review.json` obligation (a half-renamed or mid-panel dir is mixed), when such an entry exists for the directory the skill must NOT present the offer as actionable — surface the pending obligation instead, since acceptance is guaranteed to refuse

## Boundaries

### Always Do
- Use `strip_artifact_prefix(name: str) -> str` for stripping a prefix from an artifact basename already in hand — at exact-equality gates and `TERMINAL_FILENAMES` membership tests. The stripped result is honored **only when the stripped basename is in the known-artifact set** `{spec.md, design.md, tasks.md, SCOPE.md, ARCHITECTURE.md, PLAN.md}`; a stripped name outside that set is treated as a non-artifact (prevents over-match on user-owned files like `12_factor_notes.md`).
- Use `resolve_artifact(dir: Path, bare_name: str) -> Path` for all construct-then-stat read sites: probe bare first, fall back to the prefixed form, and raise an explicit ambiguity error if both exist. This is the single chokepoint where ambiguity detection lives — do not implement N independent local fallbacks.
- Add both `strip_artifact_prefix` and `resolve_artifact` to `telescoping-sdd/scripts/blueprint_common.py` (already the shared home for `compute_content_hash`, `content_for_hashing`, `verify_content_hash`, etc.) so all callers use one implementation and cannot drift on the regex.
- Keep `TERMINAL_FILENAMES` as a frozenset of BARE names; call `strip_artifact_prefix` before the membership test — do not add prefixed variants to the frozenset itself (that would require maintaining 8 entries instead of 4).
- Keep both copies of `panel-review.md` (blueprint and SDD tiers) identical in their treatment of the artifact-prefix resolution rule — the mirror discipline is load-bearing.
- Both `SKILL.md` files must use the prefixed path forms in command examples by the time the feature ships.
- Assert the hash-safety invariant in both the spec prose and a test: `verify_content_hash(content, stored_hash)` must return True after a pure rename. Note that the **content hash** is filename-independent; however the `.sdd/pending-review.json` marker is keyed by relpath, so the renamer must additionally preserve that marker (see R4).
- Default-on emission has **no opt-out flag in v1**; bare names remain permanently valid via the additive resolver. A user who dislikes the prefix may keep bare names indefinitely — the resolver accepts both. A future opt-out flag is out of scope for this feature.
- Ship R1 + R2 (resolution tolerance) fully green before shipping R3 (default-on emission) — see Implementation Sequence.

### Ask First
- During implementation, confirm the precise in-flow insertion point(s) for the interactive renamer offer in each skill if more than one reasonable point exists (Q3 is settled as "interactive offer + CLI + WARN"; only the exact prompt location within each skill's flow is a remaining design detail).

### Never Do
- Never touch the `specs/F<n>-<slug>/` directory grammar or `spec_dirname.py` slug logic — directory naming and file naming inside directories are deliberately independent concerns.
- Never rename files in a way that changes their content — the renamer must be a pure filesystem rename with no content modification.
- Never add prefixed variants to `TERMINAL_FILENAMES` directly — the frozenset stays as 4 bare names; the stripping is done pre-test.
- Never silently pick one file when both `spec.md` and `01_spec.md` exist in the same directory — `resolve_artifact` must surface an explicit ambiguity error.
- Never invalidate an existing content hash through a rename — the content hash is filename-independent; a pure rename is hash-safe. But the renamer must also preserve the `.sdd/pending-review.json` marker (keyed by relpath), so it must refuse to rename any directory that has a pending-review entry for one of its artifacts.
- Never modify `arch_config.py` line 116's directory check — it is confirmed safe and out of scope.
- Never apply prefix-strip resolution to files whose stripped basename is not in the known-artifact set — do not over-match user-owned files with two-digit numeric prefixes.

## Decision Points

- **Shared helper location (settled):** Both `strip_artifact_prefix` and `resolve_artifact` live in `telescoping-sdd/scripts/blueprint_common.py`. The design phase must finalize exact signatures, return contracts, and the error format/exit code from `resolve_artifact` on ambiguity.

- **Ambiguity check timing:** The design phase must define whether the ambiguity check runs eagerly (at directory-scan time, before any validation) or lazily (when the specific artifact is first accessed by `resolve_artifact`). Eager is safer (catches conflicts before confusing downstream errors); lazy is simpler. Pick one and apply consistently.

- **Resolver implementation pattern (settled — pattern (a)):** No site discovers artifact *files* by globbing — artifact basenames are always construct-then-stat (every read site builds an exact path like `spec_dir / "spec.md"` or `blueprint_dir / "PLAN.md"` then stats it). The two directory walks that do exist — `reconcile.py:163` and `validate_blueprint.py:550`, both `sorted(...iterdir())` — enumerate spec-*directory* names, then construct artifact paths *inside* each directory (which themselves route through `resolve_artifact`). This forecloses pattern (b) (per-call-site strip-the-found-name), which presupposes a discover-the-artifact-file-then-match step that does not exist. The committed pattern is (a): a single `resolve_artifact(dir, bare_name) -> Path` chokepoint that probes bare-then-prefixed and raises on ambiguity. All ~47 construct-then-stat sites route through this function. The global ambiguity guarantee holds precisely because there is one chokepoint, not N independent fallbacks. Remaining open design details (exact signature, eager-vs-lazy scan, error format) are for the Design phase.

- **Renamer location (settled):** The renamer is a new standalone script `telescoping-sdd/scripts/artifact_prefix.py`. Clean separation from `spec_dirname.py` (which owns directory naming); consistent with the Project Structure in this spec. Q1 is closed.

- **`tasks-python.md` / `tasks-java.md` scope (settled):** These names exist only in `archive_pass.py`'s `TERMINAL_FILENAMES` frozenset (line 104), its error string (line 661), and `test_archive_pass.py:820`. They are never emitted as user artifacts — the emitted artifact is always `tasks.md` / `03_tasks.md`; the real templates are `tasks-template-python.md` / `tasks-template-java.md`. The renamer's target mapping covers only the six canonical artifacts (`spec.md`, `design.md`, `tasks.md`, `SCOPE.md`, `ARCHITECTURE.md`, `PLAN.md`). The `TERMINAL_FILENAMES` membership test still strips `^\d{2}_` uniformly, so a hypothetical `03_tasks-python.md` would match defensively — but this is defensive-registry coverage, not user-artifact coverage. Q2 is closed.

- **Prefix regex (settled):** `^\d{2}_` — anchored at basename start, exactly two digits, separator `_`. Rejects `1_` (one digit), `01a_` (letter after digits), `100_` (three digits). Combined with the known-artifact-set guard (strip result must be in the artifact set to be honored). Q5 is closed.

- **Renamer surfacing (settled — Q3):** The renamer is surfaced through THREE channels: (1) the standalone CLI (`artifact_prefix.py`); (2) the passive non-blocking validator WARN on a **mixed-state** directory (R7); and (3) an **interactive offer in the skill flow** — both `project-blueprint` and `spec-driven-dev` interactively offer to run the renamer when they detect a **mixed** state (same mixed-only trigger as the WARN — never on uniformly-bare) in an interactive session, at most once per session and suppressed after a decline. The offer's non-interactive/CI suppression keys off a concrete interactivity signal (e.g. absence of a TTY or a CI env marker); the exact signal and the in-flow insertion point(s) are Design details, but the suppression must be a positive, testable observable (the offer is absent from output under that signal), not a manual attestation. Q3 is closed.

- **Dogfood this repo's own specs (settled — Q4):** At implementation, the renamer is run on this repo's own `specs/*/` artifacts so they adopt the prefixed form, keeping the canonical example a practitioner learns from consistent with the taught default. This is hash-safe and requires no re-approval (it exercises the same renamer end users get). **Ordering:** run the dogfood rename **last** — after all in-repo specs are sealed/approved with no open `.sdd/pending-review.json` entries — and treat this feature's own `specs/artifact-ordering-prefix/` explicitly: do not rename it while its own `tasks.md` is being ticked mid-implementation (R4's pending-review refusal de-risks this, but the order must be explicit; the rename is hash-safe regardless). Q4 is closed.

- **Definition-of-done inventory gate:** Completing the exact-equality-gate + construct-site inventory is a definition-of-done gate for this feature: zero `== "<artifact>.md"` equality gates, zero un-`strip_artifact_prefix`-wrapped `in TERMINAL_FILENAMES` membership tests, and zero un-resolver-wrapped `dir / "<bare>.md"` artifact constructions remain outside test fixtures, verified by grep before merge. (The grep pattern set must include `in TERMINAL_FILENAMES` membership, not only `==` equality and `dir / "X.md"` constructions, so the gate's mechanical coverage matches its stated complete-set purpose.) The realistic code blast radius is ~50 sites across the two validators + `render_business_brief.py` + `reconcile.py` + `archive_pass.py` + `blueprint_common.py`; ~70 prose/template/agent references are a separate, lower-risk doc sweep. This gate supersedes any claim that the current site list is already exhaustive.

### Implementation Sequence

Resolution tolerance must land and be green before default-on emission:

- **Increment 1:** R1 + R2 + the resolver-side ACs of R6 (resolution tolerance + its strip/`resolve_artifact`/ambiguity/`TERMINAL_FILENAMES` regression tests). Emission still bare — fully backward-compatible, zero observable output change for existing users, provable by tests alone.
- **Increment 2:** R3 (flip default-on) + R4 (renamer) + R7 (mixed-state surfacing) + the renamer-side ACs of R6 (the renamer hash-safety and pending-state tests, which exercise R4 and therefore cannot be green until `artifact_prefix.py` exists).

**R6 is split by dependency wave** — its resolver-side ACs land in Increment 1; its renamer-side ACs (the hash-safety-after-rename and pending-state cases) land in Increment 2 alongside R4. A "whole of R6 green in Increment 1" gate would be unsatisfiable.

**Both increments ship in the same MINOR release** — the split is an internal landing order, not a release boundary. Shipping a resolver with nothing emitting the prefixed form would be dead weight to end users, so the resolution tolerance and the default-on flip release together.

This dependency is a Boundary (see Always Do) and must also be stated in R3's implementation notes: default-on emission must not ship before the resolver tolerates the prefixed form at every site.

(Design-phase handoff: the resolver-side vs renamer-side R6 AC groupings above are stated at increment granularity because they are load-bearing for the ship-order constraint; Design will re-pin them against the final `test_artifact_prefix.py` structure.)
